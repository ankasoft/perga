# Decisions

Every ambiguity in the build specification that was resolved during implementation
is recorded here, with the rationale. Newest entries at the bottom of each
milestone section.

---

## M0 — Repository foundation

### D1: MSRV pinned to 1.95

Section 5.1 asks for "the stable release current when you start, minus two minors".
Implementation started on Rust 1.97.1, so `rust-version = "1.95"`. Verified in CI by
a dedicated `msrv` job that reads the value out of `Cargo.toml` rather than
duplicating it, so bumping the manifest bumps the CI job.

### D2: `tui-textarea` replaced with `tui-textarea-2`

Section 5.2 mandates `tui-textarea` for the editor widget. The published
`tui-textarea` 0.7.0 depends on `ratatui ^0.29`, while `tui-markdown` 0.3.9 — also
mandated — is built on `ratatui-core` 0.1.2, the 0.30 line. Holding both would put
two incompatible `ratatui` versions in the tree: the textarea widget could not be
rendered into a frame produced by the other version, and the duplicate would be
flagged by the `bans` section of `deny.toml`.

`tui-textarea-2` 0.13.2 is the maintained fork of the same crate, published under
the same `tui_textarea` library name with the same API, licensed MIT, and built on
`ratatui-core` 0.1.x. Adopting it aligns the whole tree on one `ratatui` version.
The `search` feature is enabled, since Section 9.8 says the editor's own search is
to be used rather than reimplemented.

Revisit if upstream `tui-textarea` publishes a `ratatui` 0.30 release.

### D3: `unicode-width` pinned to 0.2.0

`ratatui` pins `unicode-width = "=0.2.0"` exactly. Section 5.2 requires
`unicode-width` as a direct dependency for CJK and emoji column widths, so the
direct dependency is written as `"0.2.0"` to unify on the version `ratatui` already
carries. Section 0.7 forbids hand-writing versions to pin them; this is not a pin
for its own sake but the only version that resolves.

### D4: `tui-markdown` default features disabled

`tui-markdown`'s default feature set includes `highlight-code`, which pulls its own
`syntect` with the default `onig` backend and an `ansi-to-tui` round trip. Section
5.2 mandates `syntect` with `default-features = false, features = ["default-fancy"]`
because the `onig` backend links a C library and breaks static musl builds, and
Section 9.2 specifies perga's own code-block highlighting with a per-`(language,
content_hash)` cache. `tui-markdown` is therefore taken with
`default-features = false` and code highlighting is done by perga.

### D5: `CC0-1.0` added to the `deny.toml` licence allow list

Section 16.6 lists the permissive licences to allow and instructs that a dependency
introducing a licence outside the list be replaced rather than the list widened.
`notify`, which Section 5.2 mandates for filesystem watching, is published under
`CC0-1.0`. CC0-1.0 is a public-domain dedication — strictly more permissive than
every other entry on the list, with no attribution or reciprocity obligation — and
replacing a dependency the specification names is a larger deviation than admitting
it. The entry is annotated in `deny.toml` with the crate that requires it.

### D6: unmaintained-crate advisories scoped to direct dependencies

Section 16.6 asks cargo-deny to "deny on any RUSTSEC vulnerability, warn on
unmaintained crates". cargo-deny 0.20 expresses this with
`advisories.unmaintained`, whose values are `none`, `workspace`, `transitive`, and
`all` rather than a severity. `workspace` is used: unmaintained advisories are
reported for perga's own direct dependencies and not for crates buried inside them.

The two advisories currently suppressed by this scoping are `bincode` 1.3.3
(RUSTSEC advisory: complete, not in need of updates) and `yaml-rust` 0.4.5
(RUSTSEC-2024-0320), both reached only through `syntect`, which Section 5.2
mandates. Neither is a vulnerability; both are maintenance-status notices with no
safe upgrade available from perga's side. Vulnerability advisories remain a hard
failure at every depth.

### D7: `duplicate major version` skips

`bans.multiple-versions` is `deny`, qualified by Section 16.6's "where avoidable".
Four duplicates are not avoidable from perga: `signal-hook@0.3` (pulled by
`crossterm` 0.29, while Section 5.2 requires `signal-hook` directly, now at 0.4),
and `syn@2`, `hashbrown@0.16`, and `itertools@0.14`, all transitive build-graph
churn in the proc-macro and parser ecosystem. Each is listed in `bans.skip` with a
comment. The list is reviewed on every dependency bump and entries are removed as
upstreams catch up.

### D8: Man page and completions are not generated by `build.rs`

Section 16.5 requires this and the reasoning is recorded here for completeness:
sharing the `clap` definition with a build script means either duplicating the CLI
module or `#[path]`-including it, both of which drift. `--generate-man` and
`--generate-completions <shell>` are implemented in the binary and invoked by the
release pipeline and by every packaging artefact against the freshly built binary.

### D9: Development is happening on macOS; Linux verification is deferred

perga targets Linux only (Section 4) and the specification forbids
`#[cfg(target_os)]` branches for other platforms. The development machine available
for this work runs macOS. No macOS-specific code is being written and no
cross-platform dependency is being added for its sake, but the following cannot be
verified locally and must be confirmed by CI or by the owner on Linux:

- `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` static builds
  (covered by the `build` job in CI).
- inotify behaviour, including the `max_user_watches` degradation path
  (Section 9.9).
- `xdg-open` handoff for external links and non-Markdown targets (Section 9.5).
- `SIGTSTP`/`SIGCONT` suspend and resume against a Linux terminal (Section 12).

Every one of these is exercised by the Linux CI jobs, which are the authority.
